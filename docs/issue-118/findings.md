## Changes and invariants

1. `scripts/btc4h_continuous_forward.py`: new version `btc4h-continuous-v2-ridge100`. Issue only `[S+10m,S+15m)`, prefetch `[S+8m,S+15m)`, bounded wait <=120s. Target remains the same origin-relative five-minute bar closing `S+255m`; actual issuance-to-close is disclosed as **240–245 minutes**, not exactly 240 minutes. Training uses identical origin-relative labels, same features, ridge, 10-day history, and four comparators. No post-outcome tuning or shifting a trained label to an unrelated future target. Actual issue timestamp is sampled after computation and checked again. No forecast at +5/+16/+42/+80 minutes; +5 is early, the others late. A duplicate origin cannot be replaced even under a different version.
2. `scripts/btc4h_delivery_integrity.py`: canonical JSON line including newline has SHA256; version/origin/issue/target must match receipt; commit must be 40 lowercase hex characters; timestamps must be UTC; receipt before target **open**. For v2, first-party remote confirmation must itself leave >=240 minutes to target close. Workflow fetches the remote ref, compares SHA and complete bytes before writing a receipt. Scoring reads the forecast from the referenced Git commit. First-party evidence is never described as independent third-party attestation.
3. Existing v1 rows remain interpretable and scoreable with their actual, shorter horizons. New scores bind the canonical forecast digest and actual lead. Matching checks recompute all model losses/directions, require an observed mature candle, and refuse wrong identity/hash. Missing candles stay pending. The issue phase avoids reading old score/receipt ledgers so malformed older evidence does not block a fresh calculation; publication still fails closed on malformed persisted evidence. Corrupt score data fail scoring visibly.
4. `.github/scripts/publish_btc4h_continuous.sh`: original append-only byte-prefix validation retained, plus duplicate/missing origin rejection. Non-fast-forward pushes fail; do not rebase/rewrite/relabel evidence to win a race. The next bounded attempt reloads remote state. ## Scheduling decision and limitations

This repository is public. Use existing standard hosted Actions only; no new service or paid resource. Five bounded starts per origin (30/day), usually seconds of research work plus setup; only the +8 attempt can intentionally wait, for <=2m. Job timeout remains 25m, concurrency one writer, no busy-loop daemon. This is an incremental free scheduling improvement, **not a guarantee**: Actions cron can be delayed/dropped, running jobs can queue/collapse retries, a +20 recovery run can also be late, and Git/API failures may miss the window. Total Actions outages cannot be detected by the same unavailable scheduler; the existing external reader must check report heartbeat age (>4h30m). No additional ChatGPT task was created or changed.

The formal workflow is deliberately unchanged under the frozen-study restriction. Its historical and continuing green-job/no-issue behavior remains an explicitly unresolved formal-workflow observability limitation, although this report exposes its missed slots. A formal workflow amendment needs separate review; do not infer this PR repaired the protected study.

Strict timing requires a separately approved always-on worker or independent dispatcher. Prefer an **already approved existing server**, if one exists: systemd timer/worker starts prefetch at S+8, bounded retries before S+15, UTC clock synchronization, atomic single-writer lock, same Git evidence validation, +20 scoring, heartbeat monitored by a separate existing reader. Use least-privilege existing repository credentials only after their suitability is reviewed. Do not create secrets here. An external cron calling workflow_dispatch reduces cron-dispatch risk but still queues on Actions and cannot supply a strict issuance SLA. A managed worker is an alternative only after explicit service/budget/credentials approval; none was provisioned. Keep the formal trial isolated in any migration.

## Risk and rollback

The deliberately narrower window lowers opportunistic issuance counts compared with misleading v1; this is the intended integrity tradeoff. A late push leaves an immutable raw but unaccepted row, and a partial publication cannot be promoted by a later fabricated receipt. Fail-closed receipt/corruption checks can stop scoring/report publication and require investigation, not record deletion. Git receipts are first-party only.

Rollback by disabling the rolling workflow or reverting the code-only PR after review; preserve all data branches and new v2 evidence. Never restore the old permissive issue guard as a purported four-hour solution. Do not modify the formal protocol or model to hide attrition. Keep the issue open until live acceptance is recorded.
